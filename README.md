# pH-Responsive Carboxyl-Functionalized Graphene Quantum Dots for Anticancer Drug Delivery

Computational dissertation project — Shomari A. Johnson
CDSE (Computational Biology & Bioinformatics), Jackson State University
Interdisciplinary Center for Nanotoxicity · advisor: Dr. Jerzy Leszczynski

This repository is the computational record for the dissertation. It contains
the inputs, scripts, configuration, run log, and derived results needed to
reproduce every reported number. Large binary outputs live outside the
repository and are indexed here by checksum — see `docs/storage_map.md`.

---

## Scientific Scope

A carboxyl-functionalized graphene quantum dot (circumcoronene + one edge
–COOH, 75 atoms) is evaluated as a pH-responsive nanocarrier for four
anticancer agents: erlotinib and gefitinib (EGFR inhibitors), venetoclax and
ABT-737 (Bcl-2 inhibitors).

| Phase | Question | Method |
|---|---|---|
| **I** (current) | How strongly does each drug load onto the GQD, and why? | DFT: B3LYP-D3(BJ)/6-31G(d,p), SMD water; M06-2X/6-311+G(d,p) validation |
| **II** | Does the carboxyl protonation state release the drug in the acidic tumor environment? | pH-dependent DFT, ΔΔG, relaxed PES scans |
| **III** | Does the released drug still engage its protein target? | AutoDock Vina, GROMACS, MM/PBSA |

Only Phase I is scaffolded in this repository. Phase II and III directories are
created when that work begins, not before.

## Computational Environment

The MCSR execution-environment transition has been validated and closed for Gaussian production.

**Historical / currently preserved execution layer**

- **Cluster:** Maple, Mississippi Center for Supercomputing Research (MCSR)
- **Scheduler:** OpenPBS
- **Gaussian build used for accepted historical/current Maple work:** Gaussian 16 Rev C.01 / `g16-c01-avx2`
- **Established DFT allocation:** 16 cores, 32 GB
- **Submission wrapper:** `scripts/run_gaussian.pbs` — retained as the historical Maple execution layer and must not be overwritten.

**Active production environment**

- **Cluster:** Magnolia
- **Scheduler:** Slurm
- **Gaussian build reported by MCSR:** `g16-c02-avx2`, CPU-based
- **Production rule:** Maple is closed to new Gaussian production work. New Gaussian production proceeds on Magnolia through the validated Slurm workflow.
- **Validated wrapper:** `scripts/run_gaussian_magnolia.slurm` is committed and validated on `main`.
- **Platform validation:** `B3LYP-ERLOTINIB-MAGNOLIA-VALIDATION-001` (Slurm job 320607, node019) reproduced the accepted Maple Erlotinib baseline at the reported SCF, ZPE, Gibbs, optimization, and frequency gates and is classified `ACCEPTED_PLATFORM_VALIDATION`.

The scientific method is unchanged by the platform transition: B3LYP-D3(BJ)/6-31G(d,p) with SMD water for primary optimization/frequency work, with the established downstream validation workflow.

Local analysis environment: `environments/environment.yml`.

## Reproducing a Calculation 

Historical Maple examples below are retained for provenance. New Gaussian production uses the validated Magnolia/Slurm execution layer.

```bash
# 1. Commit the input before submitting (the run log records the commit hash)
git add calculations/phase1_dft/b3lyp/inputs/cooh_gqd_b3lyp_optfreq_v01.com
git commit -m "Add B3LYP optimization input for COOH-GQD"

# 2. Submit
qsub -N cooh_gqd_b3lyp \
     -v RUN_ID=DFT-COOH-GQD-001,INPUT=calculations/phase1_dft/b3lyp/inputs/cooh_gqd_b3lyp_optfreq_v01.com \
     scripts/run_gaussian.pbs

# 3. Monitor
qstat -u "$USER"

# 4. Verify (the job runs this automatically; run it again any time)
scripts/verify_gaussian.sh archive/logs/cooh_gqd_b3lyp_optfreq_v01.log \
                           calculations/phase1_dft/b3lyp/summaries

# 5. Rebuild the run log and commit the record
scripts/build_run_log.sh --write
git add run_log.tsv calculations/phase1_dft/b3lyp/{prov,summaries}
git commit -m "Record B3LYP optimization of COOH-GQD (DFT-COOH-GQD-001)"
git push
```

Those five commands are the entire operating loop. Every job in the project is
submitted, verified, and recorded exactly this way.

## The Run Log

`run_log.tsv` is **generated**, never hand-typed. Each job writes a provenance
file about itself (job ID, node, commit, input and output checksums) and the QC
gate writes a summary (termination, optimization status, imaginary frequency
count, energies). `scripts/build_run_log.sh` assembles both into the table.

Hand annotations go in `run_notes.tsv`, joined on `run_id`. Rebuilding the log
therefore never destroys anything one writes.

The ledger deliberately separates two concepts:

- `status` = execution/QC outcome generated from the computational record;
- `scientific_disposition` = current scientific interpretation, such as
  `ACCEPTED_CURRENT`, `ACCEPTED_COMPARISON`,
  `SUPERSEDED_STRUCTURAL_MODEL`, or `RETAINED_FREQUENCY_FAILURE`.

A run may therefore remain `status=PASS` while being scientifically superseded.
This preserves the historical fact that the calculation executed successfully
without incorrectly presenting an invalidated molecular model as a current
scientific baseline.

Failed and superseded runs stay in the log permanently, with the reason
recorded. A clean log with no failures in it is not evidence of good work; it
is evidence of a deleted history.

## Quality-Control Gates

`scripts/verify_gaussian.sh` is the gate between stages. It exits non-zero on
abnormal termination, an incomplete optimization, or any imaginary frequency,
and the exit code identifies which. No energy enters a results table until this
script has passed on the log that produced it.

## Reproducibility Limitations

- Gaussian 16 is proprietary; exact reproduction requires a licensed copy. Accepted historical Maple work used Rev C.01, while the validated Magnolia production environment uses Rev C.02.
- SCF convergence paths are hardware- and compiler-dependent; final energies are
  reproducible to the convergence threshold, not bit-for-bit.
- Checkpoint files are binary and version-specific; the plain-text inputs and
  the recorded geometries are the durable record.
